# ChessTrainer — правила совместной работы

## Как помогать владельцу проекта

- Владелец проекта хочет писать основную часть кода самостоятельно.
- По умолчанию не реализуй задачу за него. Сначала помоги сформулировать проблему, задай наводящий вопрос, предложи 2–3 направления и объясни компромиссы.
- Пиши или изменяй код только после прямой просьбы: «сделай», «реализуй», «исправь», «напиши код» и подобных формулировок.
- Если владелец показывает код и просит подсказку, не выдавай сразу готовое решение. Начни с наблюдения, следующего диагностического шага или небольшого псевдокода.
- Если владелец просит ревью, указывай конкретное место, риск и способ самостоятельно проверить гипотезу.
- Не расширяй согласованный объём работы без необходимости. Особенно не добавляй auth, billing, сложные паттерны и инфраструктуру до появления реального сценария, которому они нужны.

## Продукт и текущий фокус

ChessTrainer — русскоязычный персональный AI-тренер для игроков примерно 700–1800 Elo. Продукт должен объяснять, почему игрок допускает ошибки и что замечать в похожих позициях.

Stockfish определяет оценки, лучшие ходы и продолжения за обе стороны. Будущая LLM превращает проверенный структурированный анализ в объяснение, учитывает вопросы и намерения игрока, но не определяет лучшие ходы самостоятельно.

Текущий фокус backend — тренировочная игра с ботом:

1. Создать партию, выбрать сторону и сложность соперника.
2. Принять и проверить ход на сервере, сохранить позицию и необходимые фоновые задания.
3. Выполнить анализ и ответный ход бота вне HTTP-запроса.
4. Сохранить результаты и доставить уведомления через SSE.
5. Дать игроку возвращаться к ходам и исследовать альтернативные ветки.

Это целевой сценарий текущей работы, а не утверждение о готовности всей цепочки. Реализованные части и пробелы перечислены ниже.

Импорт Chess.com/PGN и разбор загруженных партий остаются направлением продукта; первоначальный план начинался с этого сценария. LLM-объяснения, вопросы тренеру о намерениях игрока и обучение дебютам — последующий этап. Постоянные персонажи-боты со своим стилем также относятся к будущему развитию.

## Структура репозитория

Состояние сверено с кодом 2026-10-26. При продолжении работы проверяй соответствующие файлы: этот снимок не заменяет чтение реализации.

- `BackChess/` — ASP.NET Core HTTP API, Identity, регистрация зависимостей, отправка почты, фоновый `Services/EngineJobWorker.cs`, bridge для SSE и контракты событий в `Models/Events/`.
- `ChessInfrastructure/` — сущности и их правила в `Entities/`, аккаунт в `Identity/User.cs`, EF-контекст `Storage`, типизированный доступ к конфигурации `Config` и общие модели анализа в `Models/Analysis/`.
- `ChessTrainer/` — UCI-адаптер `StockfishEngine`, парсер `EngineInfoMapper`, сервис сценариев `ChessEngineService`, проверка ходов `ChessMoveValidator` и конвертер `ChessMoveConverter`.
- `Test/` — консольные эксперименты и ручной запуск, не проект автоматических backend-тестов. Сейчас перед примером Stockfish стоит эксперимент с `Task.Run` и ранний `return`, поэтому запуск проекта сам по себе не проверяет движок.
- `frontend/` — React + TypeScript + Vite UI с локальной игрой, просмотром/загрузкой PGN и демонстрационными анализом и тренером; интеграция с backend отсутствует.
- `stockfish/` — локальные исходники и бинарник движка; локальный путь для ручных запусков — `stockfish/src/stockfish`, совместимость бинарника с окружением нужно проверять.
- `compose.yaml` — PostgreSQL и smtp4dev для локальной проверки почты.

Текущие зависимости проектов: `BackChess -> ChessTrainer -> ChessInfrastructure`, также `BackChess -> ChessInfrastructure`. Worker находится в `BackChess` и может использовать и сервис движка, и bridge без циклической ссылки. Обратную ссылку из `ChessTrainer` на `BackChess` добавлять нельзя.

По решению владельца `ChessDomain` объединён с `ChessInfrastructure`. Сейчас сохраняем простую структуру с фоновым worker. Разделение на Domain/Application/Infrastructure или отдельный исполняемый worker допустимо при конкретной необходимости, но не является задачей само по себе. Старые названия `ChessCoach.*` не описывают существующие проекты и не требуют переименования.

## Принятые решения о модели

### Аккаунт, игрок и бот

- `User` — учётная запись ASP.NET Core Identity, `Player` — участник партий, человек или бот. `BotId` в запросе создания партии означает `Player.Id` бота.
- Человек определяется через `Player.IsHuman`, связь с аккаунтом — nullable `UserId`. Начальный человеческий профиль создаётся при регистрации.
- Регистрация аккаунта, назначение роли и создание профиля объединены транзакцией: методы Identity могут вызывать сохранение самостоятельно.
- Стандартный `NameIdentifier` остаётся идентификатором аккаунта. `PlayerClaimsPrincipalFactory` добавляет отдельный claim `playerId`, получая его по связи аккаунта с профилем.
- Активную партию и текущую позицию в claims не храним. При изменении партии сервер проверяет участие игрока, очередь хода и версию.

### Партия и дерево ходов

- Режимы: `Training` — обучение с анализом и планируемыми возвратами; `BotPractice` — игра с ботом с планируемыми возвратами; `Standard` — обычная игра. Сейчас API создания реализован для `Training`.
- Узел `Move` хранит `GameId`, `PlayerId` автора, `ParentMoveId`, `UciMove`, `PlyNumber`, `FenAfter` и время размышлений при наличии. Узлы создаются через `CreateFirst`/`CreateChild`, данные и родительская связь после создания не меняются. Автор передаётся явно, фабрики проверяют его участие в партии; очередь проверяется по FEN вызывающим кодом.
- `Game.StartFen` задаёт начальную позицию. Актуальная FEN берётся из `CurrentMove.FenAfter`, а при `CurrentMoveId == null` — из `StartFen`; пересчитывать все предыдущие ходы ради неё не требуется.
- Очередь определяется по FEN. Чётность `PlyNumber` не определяет цвет: начальная позиция может быть с ходом чёрных.
- Возврат задуман как переход к конкретному узлу, затем возможна новая ветка. Старые узлы сохраняются. Отдельные параллельные списки `originalMoves`/`currentMoves` не нужны. Backend-методы возврата ещё не реализованы.
- `CurrentMoveId` — текущая позиция, `FinalMoveId` — конец сохранённой итоговой ветки. Итоговую последовательность можно собрать по цепочке родителей `FinalMoveId`; просмотр другой ветки не должен менять итог партии.
- `Game.Version` — concurrency token с `[ConcurrencyCheck]`. Клиент передаёт `ExpectedVersion`; принятое изменение позиции увеличивает версию, конфликт возвращает HTTP 409.
- Сложность фиксируется в `Game.OpponentSkillLevel` и копируется в задание бота. Сейчас используется Stockfish Skill Level 0–20, это не численное Elo игрока.

### Фоновые задания и результаты

- Сценарии разделены на `MoveAnalysisJob` и `BotMoveJob`. Прежняя универсальная сущность `GameStateJob` с `Kind` удалена; возвращать её без нового обоснования не нужно.
- `MoveAnalysisJob` содержит `GameId`, `MoveId`, обязательный `RecipientPlayerId`, nullable `ParentMoveId`, снимки `FenBefore`/`FenAfter`, глубину, статус, ошибку и время создания. Получатель персонального анализа задаётся из проверенного контекста запроса/тренировки и может отличаться от `Move.PlayerId` автора хода. Сейчас при принятии хода получатель — текущий авторизованный игрок; при будущей обработке хода бота получателя нужно определять отдельно.
- `BotMoveJob` содержит снимок FEN, nullable `PositionMoveId`, `ExpectedGameVersion`, сложность и глубину. Первый ход бота возможен уже при создании партии: узла позиции ещё нет, используется `StartFen`.
- Перед применением будущего ответа бота нужно проверить актуальность позиции и версии, чтобы ответ из старой ветки не изменил новую позицию.
- `MoveAnalysis` связан один-к-одному с заданием через `MoveAnalysisJobId`. Прямого `MoveId` в результате сейчас нет; анализ родителя ищется через `MoveAnalysisJob.MoveId` с проекцией нужных полей.
- `MoveAnalysis.BeforeAnalysis` и `AfterAnalysis` обязательны и хранят полные `EngineMoveInfo` как EF complex properties в PostgreSQL JSONB. Nullable только входной кэш предыдущего анализа: если его нет или он не подходит по качеству/глубине, сервис рассчитывает позицию до хода заново.
- `EngineMoveInfo` сохраняет исходную оценку со стороны очереди хода и PV за обе стороны. `MoveAnalysisInfo` нормализует оценки к стороне белых и вычисляет потерю в сотых пешки при подходящих точных оценках. Матовые оценки обрабатываются отдельно; нормализация не должна менять исходный кэш.
- Анализ `After` родительского хода переиспользуется как `Before` следующего. Лучший альтернативный ход игрока берётся из позиции до его хода; PV после хода начинается с ответа соперника.

## Движок и обработчик

- `StockfishEngine` отвечает за процесс и UCI-обмен; `ChessEngineService` — за сценарии `AnalyzePositionAsync`, `AnalyzeMoveAsync`, `GetOpponentMoveAsync`. Сущности EF и задания целиком в сервис движка не передаются.
- Проверка легальности и SAN/UCI-конвертация используют Gera.Chess. HTTP-модель хода сейчас принимает SAN, сохранённый ход и команды движка используют UCI; преобразование требует исходной позиции.
- Один экземпляр сервиса владеет одним процессом Stockfish и выполняет поиски последовательно. Блокировка охватывает настройку, установку позиции и поиск целиком. Параллельные вызовы этого экземпляра не дают параллельных поисков; для этого позже потребуется ограниченное число отдельных процессов.
- `gameId` передаётся в операции движка. При первом поиске и смене партии отправляются `ucinewgame` и ожидание готовности; между поисками одной партии процесс переиспользуется.
- После сбоя обмена или таймаута адаптер завершает процесс; сервис нужно освободить и создать заново. Ошибки сохранения БД и проверки входных данных не требуют перезапуска Stockfish.
- Анализ по двум FEN не восстанавливает историю повторений позиции; не считать этот путь полноценной проверкой ничьих по истории партии.
- `BackChess/Services/EngineJobWorker.cs` зарегистрирован через `AddHostedService` и пока обрабатывает только анализ ходов, последовательно и с расчётом на один экземпляр обработчика. Задания загружаются с tracking, предыдущие анализы — без tracking.
- Результат и `Completed` сохраняются одним `SaveChangesAsync` на задание. Промежуточной записи `Running` сейчас нет; незавершённое вычисление при остановке остаётся `Pending`.
- При ошибке отсоединяются только текущее задание и его несохранённый результат, затем записываются `Failed` и причина. Остальные задания остаются в трекере; успешные имеют состояние `Unchanged`. Общий `ChangeTracker.Clear()` и повторный `Attach()` не нужны.
- Несколько worker/экземпляров приложения потребуют отдельного атомарного захвата заданий и восстановления после сбоев; текущая схема этого не обеспечивает.

## SSE и восстановление

- Для событий выбран встроенный SSE через `TypedResults.ServerSentEvents`. SignalR для этого не обязателен; старые упоминания SignalR в планах и frontend README не меняют текущий выбор.
- `ChessBridgeService` без generic-параметра хранит `Channel<GameEvent>` в памяти по `(gameId, playerId)`, внутри — отдельный канал на `connectionId`. Это позволяет иметь несколько вкладок без конкуренции читателей за один канал. Закрытые каналы пропускаются через `TryWrite`, пустые группы удаляются с согласованием регистрации и отключения.
- `GameEvent` — общий DTO-контракт в `BackChess/Models/Events/`. JSON содержит discriminator `type`: `move-analyzed` для `MoveAnalyzedEvent`, `bot-move-applied` для `BotMoveAppliedEvent`. Сущности EF в события не передаются.
- Worker после успешного сохранения посылает `MoveAnalyzedEvent` по `job.GameId` и `job.RecipientPlayerId`. Событие содержит идентификаторы партии, задания, хода и сохранённого анализа. `BotMoveAppliedEvent` пока только контракт для будущего обработчика бота.
- `GET /api/games/game-events?gameId=...` проверяет авторизацию и участие игрока в партии, затем передаёт новые события через SSE `event: message`. Конкретный вид события определяется полем `type` внутри JSON. Подписка удаляется при отключении клиента.
- `connectionId` относится к конкретному подключению и может измениться после reconnect. Подписки не сохраняются в таблицу; после перезапуска клиент подключается заново.
- Результаты и состояние должны сначала сохраняться в БД, затем отправляться уведомление. Отсутствие подписчика или ошибка доставки не должны менять успешно завершённое задание на `Failed`.
- Восстановление после reconnect должно опираться на сохранённое состояние/результаты. `Last-Event-ID` сам по себе не реализует чтение пропущенных событий с сервера.

## Что ещё не подключено

- Обработка `BotMoveJob` и применение найденного хода с проверкой позиции/версии остаются TODO.
- Поток в `GameController` подключён к bridge, но восстановление пропущенных событий и отдельный API чтения анализа по `AnalysisId` ещё не реализованы. Событие сообщает о готовности результата и не содержит сами оценки. Отдельный `/events` в `Program.cs` остаётся демонстрационным потоком строк.
- Bridge — singleton в памяти одного процесса. Доставка между несколькими экземплярами приложения не реализована. Frontend ещё не подписывается на реальные игровые события.
- Backend-возвраты и переключение веток, интерфейс администрирования, LLM и чат с тренером не реализованы. Backend-импорт Chess.com/PGN также не подключён.
- EF-модель описана в `Storage`; миграций в репозитории сейчас нет. Не предполагать, что реальная схема БД соответствует модели или запись в неё проверена.

## Технические договорённости и кодстайл

- Backend: .NET 10, ASP.NET Core, EF Core, PostgreSQL; frontend: React, TypeScript, Vite, русский интерфейс и mobile-first адаптация.
- Долгие вычисления никогда не выполнять внутри HTTP request. API сохраняет соответствующее задание, worker обрабатывает его, состояние хранится в backend.
- Сохранять границы ответственности HTTP API, правил, хранения и UCI-обмена. Не создавать новые проекты или абстракции только ради «чистой архитектуры».
- Использовать nullable reference types, `CancellationToken`, структурированные логи, явные timeouts и осмысленную обработку ошибок. Время сохранять в UTC.
- Для новых и изменяемых C#-методов писать XML-комментарии с `<summary>` и `<param name="...">` для каждого параметра, а при наличии результата — с `<returns>`. Поля, свойства и значимые локальные переменные сопровождать описаниями. В конце текста комментариев и описаний не ставить точки.
- Явные `[ForeignKey]` сохранять по предпочтению владельца. Fluent-конфигурацию добавлять для необходимых связей и особенностей хранения; не дублировать конвенции EF настройкой каждого поля.
- Использовать EF Core напрямую; не добавлять generic repository и MediatR без конкретной необходимости. Не раздувать методы, интерфейсы и количество сервисов ради гипотетических сценариев.
- Не добавлять отдельные тесты на простые обратимые изменения без содержательной проверки поведения. Для изменений обработки ошибок, очереди, легальности ходов и анализа нужны соответствующие проверки.
- Новую production dependency добавлять только после объяснения, какую задачу она решает, проверки лицензии и оценки риска поддержки.
- Настройки читаются через `Config.Initialize(...)` и `Config.GetSection<T>()`; имя секции соответствует имени класса. Не заменять этот подход без согласованной необходимости.
- API keys, пароли, строки подключения и токены не передавать во frontend, не коммитить и не выводить в диагностические ответы. Для изучения конфигурации достаточно нужных ключей и безопасных значений.

## Frontend и локальные данные

- Уже есть локальная игра за обе стороны, возврат полухода, восстановление черновика, экспорт PGN и просмотр партий через `chess.js` и `react-chessboard`. Эти данные пока живут только в браузере.
- Демо-анализ находится в `frontend/src/data/mock.ts`, локальное хранение отделено в `frontend/src/data/localGames.ts`. Адаптеры должны заменяться API-клиентом без переписывания компонентов.
- Не выдавать клиентские заглушки за Stockfish-анализ. Демонстрационные evaluation, best move, пояснения и связанные позиции должны быть явно помечены как демо.
- Клиентские правила и PGN parsing допустимы для UX; каноническая проверка принятых сервером данных выполняется backend. Самостоятельно вычислять шахматную оценку в браузере не нужно.
- После подключения API состояние фоновых заданий и серверной партии восстанавливается с backend, а не хранится исключительно в React/localStorage.

## Проверки и запуск

Из корня репозитория:

```bash
dotnet restore ChessTrainer.sln
dotnet build ChessTrainer.sln --no-restore --nologo -m:1 /nodeReuse:false /p:UseSharedCompilation=false
docker compose up -d
dotnet run --project BackChess/BackChess.csproj
```

`dotnet restore` нужен при отсутствии восстановленных зависимостей или их изменении. Для запуска API нужны корректные настройки подключения, почты и `StockfishOptions`, включая путь к совместимому Stockfish. Worker запускается вместе с API и требует подготовленной схемы БД.

Из `frontend/`: `npm install` при необходимости, `npm run dev` для разработки, `npm run build` и `npm test` для проверок. Требования к окружению и локальной игре описаны в `frontend/README.md`.

Автоматического backend test project сейчас нет. Временные проверки предыдущих чатов в `/private/tmp` не входят в репозиторий и могут быть недоступны в другом окружении; не считать их постоянным набором тестов. Сборка и проверки модели/SQL без сервера не подтверждают реальную запись в PostgreSQL или полноценную интеграцию API, worker и SSE.

## Перед существенной реализацией
